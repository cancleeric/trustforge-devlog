主要變更

1. 前端/後端資產分類契約對齊（#574 / #673）

  • 變更：後端 asset_context.py 的 enum 分類（sector / layer / token_role / market_cap_tier）下沉到前端 types.ts——AssetContext 原本是 string 四欄，收斂成強型別 union，並保留 unknown 值。關鍵設計決策：型別層不綁死 enum 白名單，僅提供 isKnownXxx 判斷函式，渲染層做 fallback。
  • 風險：後端新增 enum 值時，舊前端若不升級仍可編譯（不連帶失敗），但未知值會走 unknown fallback，UI 可能顯示空白或預設態。
  • 影響：把「後端認定不明的欄位絕不用空字串冒充」的誠實性原則從文件推進到型別契約，減少跨邊界序列化時的隱性 drift。
  • 未驗證處：未確認 asset_context.py 全量 enum 值與前端 ASSET_* 常數是否 100% 一致（需型別/執行期測試覆蓋）。

2. freshness 全 stale 時標記 degraded（#537 / #674）

  • 變更：freshness.dashboard() 新增 degraded / degraded_reason 欄位與 fail-safe 判定：樣本為 0 或全 missing 標 no_data、全部 stale 標 all_freshness_stale、部分 stale 超過 degraded_stale_after 門檻標 stale_exceeds_threshold。同時回傳 last_refresh_epoch、max_stale_age_sec、affected_source_count。
  • 風險：面板消費方需讀 degraded 旗標，否則仍可能把空資料誤報成 healthy——這是 contract 變更，下游要跟。
  • 影響：觀測面板在「資料全爛」時誠實降級，符合 TrustForge 一貫的誠實性立場，不再靜默 healthy。
  • 未驗證處：新判定邏輯未經執行期測試（見下一步 checklist）。

3. replay 回填在 PIT 邊界拒絕無時區時間戳（#515 / #675；commit message 標註 CISO review passed）

  • 變更：store_backfilled_source_snapshot() 過去直接用 datetime.fromisoformat 解析 published_at，naive 時間戳會被靜默套用 host-local 時區。現在要求 timezone-aware ISO 8601，tzinfo/utcoffset 為 None 直接 ValueError 拒絕，並統一 astimezone(utc)。
  • 風險：fail-closed——任何歷史回填若來源時間戳缺時區，直接報錯而非猜時區，可能擋下原本「碰巧對」的資料。
  • 影響：歷史回填的資料完整性從「碰巧對」變成「結構上不可錯」，這是 fail-closed 的防線。
  • 未驗證處：CISO review passed 僅見於 commit message，本輪未重跑相關測試或重做 CISO 審核，僅確認程式碼變更內容。

4. deploy 腳本修復空 SNS 陣列展開（#571 / #672）

  • 變更：put_dedup_alarm.sh 原本在 set -u 下宣告 ALARM_ACTION_ARGS=()，SNS_TOPIC 為空時 ${ALARM_ACTION_ARGS[@]} 展開觸發 set -u 報錯。改法：不用陣列，直接在 put_metric_alarm() 裡用 if [[ -n "$SNS_TOPIC" ]] 分支決定是否帶 --alarm-actions/--ok-actions。
  • 風險：低；純 shell 控制流重構，行為等價（SNS_TOPIC 非空時帶相同參數）。
  • 影響：release gate 在真實 set -u 環境下能跑到綠燈的必要前提——很多「本地能過、CI 掛掉」就長這樣。
  • 未驗證處：未在本輪 CI / pre-push 中實跑兩種 SNS_TOPIC 情況。

工程意義

本輪是「契約收斂 + 誠實降級 + 資料邊界 fail-closed」三條線的同步推進。資產分類從鬆散的 string 收斂成前後端共享的強型別 union，減少跨邊界序列化時的隱性 drift；freshness degraded 標記把「觀測失靈」從靜默 healthy 變成顯式降級，符合 TrustForge 一貫的誠實性立場；replay PIT 的時區拒絕則把歷史回填的資料完整性從「碰巧對」變成「結構上不可錯」。這三者共同把系統往「可解釋、可審計、fail-closed」的信任架構再推一步。

另外，deploy 腳本的修復雖小，卻是把 release gate 在真實 set -u 環境下跑到綠燈的必要前提。
