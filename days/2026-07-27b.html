信任評分細節

公式

TrustScore = 信譽 × 0.50
           + 交叉佐證 × 0.25
           + 時效衰減 × 0.15
           − 操縱懲罰 × 0.40

操縱懲罰是減法，權重(0.40)故意比其他正項都高。設計決策：操縱偵測的「漏抓」比「誤判」風險低，但為保守，偵測本身只用啟發式關鍵詞、命中門檻刻意拉高。

分項 1：來源信譽（Source Reputation）— 權重 0.50

靜態先驗：每種來源類型有基礎信譽分，反映「客觀程度」：

來源類型基礎信譽理由
price / onchain0.95鏈上事實、價格數據最客觀
regulatory0.90官方監管公告
hoyabit0.85HOYA BIT 企業級交易所數據
price_live (CoinGecko)0.90即時市價
news0.65新聞媒體
sentiment / dev_activity0.50輔助訊號
social0.35匿名社群（最低）

動態信譽（W2 進階）：truth-discovery 迭代——長期被其他獨立來源佐證的來源信譽上調，被矛盾得多的下修。bounded 迭代（最多 5 輪）+ 收斂門檻 + 下限 clamp。離線有 Dawid-Skene EM 統計共識 fallback。

分項 2：交叉佐證（Cross-Source Corroboration）— 權重 0.25

同一主張有多少「獨立」來源也在說類似的事？

  • Token overlap 前置閘（Jaccard ≥ 0.4 才算「相似主題」）
  • 方向閘（明確看多 vs 看空不算佐證）
  • 可選 W1.5 Bedrock stance 語意分類（偵測「表面相似但實質矛盾」）
  • 同源排除：同一 publisher 正規化為同一源，同源不算獨立佐證

算法：1 - 0.5^n（n = 獨立佐證來源數）。1 源佐證 → 0.5，2 源 → 0.75，飽和 → 1.0。回音室（同源灌水）完全無效。

分項 3：時效衰減（Recency Decay）— 權重 0.15

指數衰減：decay = 0.5 ^ (age_hours / half_life_hours)

  • 鯨魚/名人交易信號：半衰期 2 小時（市場秒級反應）
  • 其他來源：半衰期 12 小時
  • 未來時間戳（壞資料）或 NaN → 保守回 0.5（中性）

分項 4：操縱懲罰（Manipulation Penalty）— 權重 0.40

兩層偵測：

  • 關鍵詞啟發式：泵/倒詞命中。否定守門：「不會暴漲」不算命中。可疑用語回填到 Evidence 供人工查看。
  • 確定性協同偵測（informational-only）：多源文字高度相似（Jaccard ≥ 0.8、≥3 來源）標記為「可能協同或聯播，供判讀」。CEO 定案：不自動扣分——分不清協同操縱 vs 合法聯播，自動扣分必然誤傷。

聚合：ScoredClaim → TrustedBrief

  • trust ≥ 0.50 → 歸入「支撐證據 supporting」
  • trust < 0.50 → 歸入「反方證據 contrarian」
  • 整體信心 = evidence_strength 綜合指標（獨立來源數 × kind 多元度 × 佐證比例 × 裸信心）→ 校準表映射
  • 低校準信心（< 0.35）或獨立來源數不足（< 2）→ abstain，不硬給方向結論

架構技術實作

三層 Pipeline 完整流程

Layer 1 — Ingestion（多源輸入）
  connectors: prices / news / social / onchain / coingecko / regulatory / hoyabit
  統一輸出：list[Document] (id, kind, source, text, timestamp, url, meta)

Layer 2 — Trust（信任提煉）
  Step 1: extract_claims(docs) → list[Claim]（句級切分 / 可選 LLM 抽取）
  Step 2: score(claims, now) → list[ScoredClaim]（確定性公式）
  Step 3: aggregate(scored, query, coin) → TrustedBrief

Layer 3 — Agent（編排 + 溯源生成）
  orchestrator.py 4 步推理鏈：
    Step 1: Bedrock #1 — Claim 抽取（LLM 輔助結構化）
    Step 2: 判斷形成（純 pipeline，不用 LLM）
    Step 3: Bedrock #2 — 帶溯源行文（強制引用 claim_id）
    Step 4: Bedrock #3 — 限制複審（選用，預算允許才執行）
  輸出：Report + Evidence List + Execution Log

關鍵技術決策

1. Bedrock 集中管理（bedrock.py）
  • 所有 LLM 呼叫唯一入口
  • 集中 token 計量、成本追蹤
  • 統一 timeout/retry 策略
  • 單點切換模型（Claude 3 Sonnet / Haiku）
  • 離線/線上模式切換一個 flag
2. 預算護欄（budget_guard.py）
  • ExecutionLog 追蹤即時剩餘時間
  • Stance 呼叫預留 25 秒（connect 3s + read 8s + report 裕量 14s）
  • Stance 配對硬上限 40 次（防 O(n²) 爆 Bedrock）
  • 預算不足時 fail-safe 降級，不 crash
3. 反作弊設計

判斷結構、證據整合、信任評分由本 pipeline 產生。Bedrock 只負責行文。Bedrock 角色嚴格限定：幫切分 claim（Step 1）、寫成可讀 narrative（Step 3）、審查報告（Step 4）。判斷本身——哪些值得信、信多少、正反方怎麼分——完全是確定性公式算的，不是 LLM 說了算。

4. 溯源鏈完整性
報告段落 → claim_id → ScoredClaim.components（四個分項）
         → Document（原始文件）→ source URL + timestamp

Evidence List（JSON）包含完整 trust breakdown、命中的操縱關鍵詞、reputation trace。

5. 純 stdlib + boto3 原則
  • 整個後端零第三方 runtime 依賴
  • 部署極簡（任何 Python 3.11 + boto3 環境都能跑）
  • 沒有 supply chain 風險
  • 容器映像極小
