主 repo 變更（TrustForge）

1. 正式執行路徑生產配套缺口——八連修止血（#1175 / #1177 / #1178 / #1179 / #1180 / #1181 / #1182 / #1184）

完成：依提交紀錄自陳，主線自 v0.27.36 把對外分析問答 API 切到正式執行處理器後，生產機器缺少對應資料表、密鑰與環境變數，導致每小時發布列車逐次在金絲雀階段失敗回滾、並曾使對外層中斷。本班一連串補救：發布列車新增前置檢查，偵測到主線含正式執行處理器但生產就緒旗標不存在時直接失敗即擋、不備份不部署（#1175）；再把止損動作前移到閘道之前，避免閘道本身不穩時連止損都走不到（#1177）；就緒旗標改為「存在即就緒」，解開「旗標要寫合併後雜湊、但雜湊要合併後才知道」的死結（#1180）。執行期兩處硬性依賴環境變數的取密鑰路徑改為環境變數優先、參數存放區次之，兩者皆無才失敗即擋（#1178 / #1181）。預算保留在交易寫入時因未被條件式引用的多餘參數而觸發驗證例外、進而讓 API 回 503，已改為僅在條件實際引用時才帶入（#1182）。金絲雀本身也修了兩處：改為兩階段送出以符合新的作用域流程（#1179），以及冪等鍵格式改用規範要求的樣式（#1184）。

價值：這是本班最實質的價值——止住了「每小時自動部署一個必然失敗的版本」這種持續消耗，並讓正式執行的密鑰不必以明文形式落在服務設定檔裡，降低憑證暴露面。

風險：止血手段是「擋住部署」，代表生產目前刻意不前進；若配套遲遲未補，主線與線上版本的落差會持續擴大，而落差愈大，日後一次補上的部署風險愈高。就緒旗標簡化為「存在即就緒」後，旗標過期失效的情境依提交紀錄自評為低風險，但本班無法驗證該判斷。

待驗證：生產配套（資料表、密鑰、環境變數）是否已建立；就緒旗標是否已寫入且內容可供稽核；對外分析問答實際送出一次能否取得完整報告。

2. 原生一次性交易整合——二十二筆連續修補（#1089 / #1174）

完成：本班有二十二筆針對原生一次性交易整合的修補，集中在三件事：把上一階段驗收過的原生產物綁定為持久宣稱、交接目錄的生命週期由自己完整持有（含巢狀日誌私有化、部分清理殘留的分類、清理根目錄範圍限縮），以及把語意證據與產物證據的摘要分離、只讀收據模式分離、原生建構收據重新釘選。測試側同步隔離注入時鐘與執行緒、釘選交接原生物件。

價值：原生執行期的產物來源與交接過程若不可信，上層所有「可驗證」宣稱都是空的；這批修補是在把該基礎補實。

風險：單一功能需要二十二筆連續修補，代表前幾輪的邊界設定反覆未收斂；此類長修補鏈通常尚有未浮現的殘留缺口。本班未實跑其驗收腳本。

待驗證：實跑原生整合驗收腳本並取得第一手通過紀錄；以刻意竄改的交接產物測試是否被正確拒絕。

3. 鯨魚警報管理端憑證控管——安全審查五項收官（#1100 / #1111）

完成：提交紀錄記載，本項經對抗式雙軌審查後提出五項問題並於本班全數關閉：傳輸層檢查移到讀取請求主體之前（原本先讀走明文金鑰才檢查，等於沒防到）、整個端點限定加密傳輸，直連時回拒；金鑰解析僅在「參數不存在」時才回退到環境變數或檔案，其餘錯誤一律失敗即擋；啟用時要求來源必須為參數存放區；清除金鑰後直接回報清除後的真實來源，避免最終一致性把剛撤銷的憑證重新快取，若殘留舊式環境金鑰則誠實回報而非掩蓋；稽核日誌記錄來源位址且永不記錄明文金鑰。

價值：「先檢查再讀取」與「清除後誠實回報」兩點修的是真正會導致憑證外洩或誤判已撤銷的缺陷，屬高價值修補。

風險：審查與測試結論僅見於提交紀錄，本班未實跑其測試、亦無獨立安全審核可背書。管理端涉及憑證寫入，權限邊界的實測缺口仍在。

待驗證：實跑該項測試取得第一手結果；以未授權身分與非加密傳輸實際打該端點，確認皆被拒絕且稽核日誌不含明文。

4. 品質驗收登錄硬化與原子批次自動注入移除（#1095）

完成：驗收登錄驗證器強化——清單的來源雜湊必須綁定預期的發行雜湊（拒絕過期或偽造清單）、拒絕結束時間早於開始時間的驗收案例、鎖定最小權限的存取政策契約（禁用萬用字元），並在文件中明確定位該驗證器目前僅為輔助性質、尚未接進自動閘道，不得當作發行證據。另移除部署腳本對原子批次環境變數的自動注入：原子批次本是分階段的人工遷移，自動注入會讓沒有對應資料表的環境從「優雅地失敗即擋」惡化成執行期直接失敗。

價值：把「看起來像證據但其實不是證據」的東西誠實標註為輔助，是稽核連續性上很重要的一筆；移除自動注入則消除了一類會把安全降級變成當機的部署陷阱。

風險：驗證器既然只是輔助，代表目前發行流程仍缺一道自動化的驗收閘道；在該閘道補上之前，發行品質仍依賴人工自律。

待驗證：驗收登錄驗證器何時接入自動閘道；接入後對一份刻意偽造的清單實測是否被擋。

5. 部署韌性、跨平台可攜性與技能異動紀錄持久化（#1159 / #1172 及部署側修補）

完成：資料目錄中含冒號的檔名改名，解除視窗系統無法取出倉庫的阻塞（#1159）；啟用前置檢查腳本在指標檔缺失或為空時，因未初始化變數而在嚴格模式下直接中止，已改為預先設空值並優雅回報缺失（#1172）；技能異動紀錄新增跨部署持久化的協調腳本（含共享鎖、首次建立父目錄、拒絕符號連結置換、父目錄符號連結失敗即擋），並把驗證納入啟用回滾流程；另修正一項因主機負載而間歇失敗的序列測試與部署測試腳本中的未定義變數。

價值：這些都是「不修就會每天扎人」的營運摩擦：開發者取不到倉庫、部署腳本莫名中止、技能紀錄每次部署被清掉。

風險：提交紀錄提到生產側的指標修復先前是以遠端指令手動處理、本班才使其在後續部署中持久，代表此前生產狀態曾以人工手段修補，該類人工修補若還有未持久化的殘留，下次部署會再度回退。間歇失敗的測試以放寬逾時處理，未根治根因。

待驗證：盤點是否還有其他僅以人工遠端指令修過、尚未持久化的生產狀態；間歇失敗測試在負載下的實際穩定度。
